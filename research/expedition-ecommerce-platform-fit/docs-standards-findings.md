## 1. The Core Data Model — What Frappe Webshop Actually Exposes

### Item Template / Item Variant / Website Item

**Item Template (Item DocType, `has_variants = 1`)**
- Created by ticking "Has Variants" on an Item record.
- Cannot be used in transactions (Sales Order, Quotation, etc.) directly. The ERPNext documentation states explicitly: "You cannot make Transactions against a 'Template'."
- Holds the master image field: one `image` field (Attach Image type, hidden in form, `in_preview = true`).
- Variant attributes are defined in a child table on the template.

**Item Attribute DocType** (source: `item_attribute.json`)
- Fields: `attribute_name` (Data, required, unique), `numeric_values` (Check), numeric range fields, `item_attribute_values` (Table → Item Attribute Value), `disabled`.
- **No color hex, no image, no swatch field.** Attribute values are purely text strings with an abbreviation.

**Item Attribute Value DocType** (source: `item_attribute_value.json`)
- Fields: `attribute_value` (Data, required) and `abbr` (Data, required).
- **Two fields total. No visual representation. No color, no image, no swatch.**
- This means color attributes like "Pearl White" are stored as plain text strings only. The system has no built-in mechanism to associate a hex color or a swatch image with an attribute value.

**Item Variant (Item DocType with `variant_of` set)**
- Created from template + attribute combinations.
- Item code generated by `make_variant_item_code()`: template code + attribute abbreviations concatenated.
- Has its own `image` field (same Attach Image field). Image defaults to template image on creation unless `use_template_image = False`.
- Source confirms: "image, pricing, taxes etc will be set from the template unless explicitly specified."
- The Item Variant Settings DocType controls which template fields propagate to variants on template save.

**Website Item DocType** (source: `website_item.json` + `website_item.py`)
- The webshop-facing record that wraps an Item for publishing.
- Image fields on Website Item:
  - `website_image` (Attach Image, hidden, print_hide; populated from Item.image automatically, overridable)
  - `website_image_alt` (Data — alt text)
  - `thumbnail` (Data, read-only)
  - `slideshow` (Link → Website Slideshow)
- The documentation states: "Website Image: automatically populated with the Image from the Item master. You can change it as well."
- **There is no per-variant image field on Website Item.** The slideshow field links to a Website Slideshow record — one slideshow per Website Item, not per variant.
- `has_variants` and `variant_of` are read-only fields fetched from the linked Item. Website Item is a template-level or variant-level record; both can be Website Items.

**Critical gap confirmed by source code (`website_item.py`):**
- `validate_website_image()` validates one image.
- `make_thumbnail()` creates one thumbnail from the primary image.
- `set_metatags()` uses `context.website_image` (singular) for OG tags.
- The variant attribute logic (`set_selected_attributes()`, `set_attribute_values()`) handles attribute selection but **does not reference images**.

## 2. Per-Variant Photo Swap — Officially Supported? Definitive Answer: No

**Finding:** Frappe Webshop has **no documented mechanism for per-variant image swap.**

Evidence chain:

1. **Item Attribute Value** has no image or color field (confirmed from DocType JSON).
2. **Website Item** has one `website_image` + one `slideshow` — both template-level, not variant-level.
3. **`variant_selector/utils.py`** (whitelisted API): `get_next_attribute_and_values()` returns matching variants, pricing info, and inventory quantity. **It does not return images.**
4. **`product_page.js`** implements image swapping on hover over alternative images only — this is thumbnail gallery hover, not attribute-selection-triggered swap. When a variant is selected via attribute dropdowns, the page performs a **full redirect** (`?variant=` URL param), not an AJAX image update.
5. **`shopping_cart/product_info.py`** (`get_product_info_for_website`): returns `price`, `qty`, `uom`, `sales_uom`, `on_backorder`, `stock_qty`, `in_stock`, `show_stock_qty`. **No image field in the response.**
6. **Forum thread** (discuss.frappe.io/t/111934): Community member reports "item-image remain the same on any variants button clicked" — unanswered question, not a solved problem.
7. **Issue #272** (webshop maintainer summary): Lists fundamental gaps but does not reference image-swap as a resolved feature.

**How the current UX works on variant selection:** The configure button triggers a modal (variant_selector). When a variant is confirmed, the URL changes to `?variant=ITEM_CODE`. The page reloads at the same route with the variant's Website Item context — which means the page re-renders with whatever `website_image` is set on that variant's Website Item record, if one exists. This is a full page reload, not a dynamic swap.

**What "works" today:** If every variant has its own Website Item record with a distinct `website_image`, variant selection (via configure → confirm → page reload) will show different images. But this requires:
- A separate Website Item record published for every variant (LT has 10,227 active variants — this is 10,227 Website Item records)
- A distinct `website_image` uploaded to each variant's Website Item
- The page reload on every color/size selection (no live swap)

**What does not work:** Clicking a color swatch and seeing the hero image update in-place without a page reload. This is not implemented and is not documented as a planned feature.

## 3. Per-Variant Pricing — Officially Supported? Yes, With Caveats

**Finding:** Per-variant pricing IS supported via Item Price records keyed to variant item codes, with template-level fallback.

Evidence from `erpnext/utilities/product.py` (`get_price()` function):
- Queries "Item Price" records by the variant's `item_code` first.
- Falls back to `template_item_code` if no variant-specific price exists.
- Returns: `price_list_rate`, `currency`, `formatted_price`, `formatted_mrp`, `currency_symbol`, `formatted_price_sales_uom`, `discount_percent`, `formatted_discount_percent`, `formatted_discount_rate`.

**Pricing Rules** (`docs.frappe.io/erpnext/user/manual/en/pricing-rule`):
- Can be applied per Item Code (variant level), Item Group, or Brand.
- Triggered by quantity thresholds, customer/party type, date ranges, custom Python conditions.
- **No documented mechanism for "attribute combination" pricing** — e.g., you cannot say "Blue + Large = $5 premium" via a Pricing Rule without writing a custom condition.
- There is a known open issue: "Webshop Prices not affected by Margin Rate in Pricing Rule" (webshop issue #268). Pricing rules are not fully honored in the webshop context.

**Practical implication for LT:** Each of LT's 10,654 Item Price records is variant-level (confirmed by the earlier DB count). The `get_price()` function will find and serve these correctly per variant. The pricing model works — but pricing rules with margin rates may not apply in webshop context (open bug).

## 4. Color Combinations as Sellable Variants — Officially Supported Model

**Finding:** The standard ERPNext variant model supports multi-attribute variants natively. A "balloon with Color=Pearl White AND Size=11-inch" is a standard variant with two attributes.

The item_variant.py `create_variant()` function builds variants from attribute combinations. The docs confirm: "if you choose Color: Red, Green and Size: Small, Medium, Large, 6 variants will be created."

**What is NOT supported natively:**
- Attribute values that are color swatches (hex or image-based) — text-only
- Dependent/conditional attributes (e.g., "show Size only after Color is selected") — the variant_selector shows all attributes simultaneously
- Hiding unavailable combinations from the UI (the selector shows all attribute values regardless of whether a valid variant exists for that combination; `get_next_attribute_and_values()` does disable unavailable options, but the UI presentation is dropdown-based, not visual)

## 5. Cart and Checkout — Official Customization Surface

**Cart module** (`webshop/webshop/shopping_cart/cart.py`):

Whitelisted methods:
- `get_cart_quotation()` — retrieves cart with addresses and shipping rules
- `update_cart()` — adds/removes items or updates quantities
- `get_shipping_addresses()` / `get_billing_addresses()`
- `place_order()` — converts quotation to Sales Order
- `request_for_quotation()` — submits quotation as RFQ
- `get_shopping_cart_menu()` — renders cart dropdown
- `add_new_address()`
- `create_lead_for_item_inquiry()` — guest-accessible
- `get_terms_and_conditions()`
- `update_cart_address()`
- `apply_shipping_rule()`
- `apply_coupon_code()` — guest-accessible
- `remove_coupon_code()` — guest-accessible

**Cart data model:** Built on Quotation DocType with `order_type = "Shopping Cart"`, `docstatus = 0`. Party is Customer or Lead. This is standard ERPNext Quotation — all ERPNext Quotation fields and hooks apply.

**Customization hooks documented in hooks.py:**
- `override_doctype_class` — can override Quotation, Item Group, Item, Payment Request classes
- `doc_events` — hooks on Item, Sales Taxes and Charges Template, Quotation, Price List, Tax Rule (validate events)
- `on_logout` — clear shopping cart
- `on_session_creation` — initialize cart counts
- `override_whitelisted_methods` — can override any of the cart's whitelisted methods

**Documented limitation from open issues:**
- "Cannot add new address or addresses in cart" (issue #301, open) — address management is broken
- "Need to add option to add multiple quantities of a product from the product page itself" (issue #324, open) — quantity increment on product page not supported
- "Allow adding items to cart without login" (issue #215, open) — forces login before shopping, only after checkout can be guest
- Guest cannot maintain shopping carts (issue #272, maintainer-documented)
- Pricing rules with Margin Rate not applied in webshop (issue #268, open)

**Cart templates:** `webshop/templates/pages/cart.html`, `cart.js`, `cart.py` — all overridable by placing same-name files in a custom app's `www/` folder.

## 6. Official Frappe v15 Hook Extension Points (Webshop-Relevant)

From `docs.frappe.io/framework/v15/user/en/python-api/hooks`:

**`override_whitelisted_methods`** — Documented, actively used by webshop itself. Last installed app wins. Allows replacing any `@frappe.whitelist()` endpoint with a custom implementation that must have the same signature.

**`override_doctype_class`** — Documented. Allows extending or replacing standard DocType controllers. Webshop uses this to override Item Group, Item, and Payment Request.

**`web_include_css` / `web_include_js`** — Documented. Injects static assets into portal pages (web.html base). This is how custom JS/CSS reaches the webshop frontend.

**`update_website_context`** — Documented. Allows adding or modifying variables available during portal page rendering. Can inject data into product page Jinja context.

**`doc_events`** — Documented. CRUD lifecycle hooks on any DocType.

**`website_route_rules`** — Documented. Maps URLs to custom controllers for clean URLs.

**`website_generators`** — Documented as DEPRECATED. "Use Has Web View in DocType instead." Still functional but not the recommended path.

**`extend_website_search_match_conditions`** — NOT documented in the official hooks reference. Not found in any official documentation.

**Template overrides:** Portal pages can be overridden by placing same-name files in a custom app's `www/` folder — they take precedence over framework defaults. This is the documented mechanism for overriding `webshop/www/all-products/index.html`, `webshop/templates/pages/cart.html`, etc.

## 7. ERPNext Core Ecommerce Primitives (What ERPNext Ships Without Webshop)

ERPNext core (without the separate `frappe/webshop` app) ships:

- **Item DocType** — with `has_variants`, `variant_of`, `item_attribute`, image field, Item Variant Settings
- **Item Attribute + Item Attribute Value** — text-only attribute definitions
- **Item Price** — price list records keyed to item_code + price_list + currency + date range + customer group
- **Pricing Rule** — discount/price override rules
- **Website Item** — the webshop-facing wrapper (moved to webshop app in v15; must install webshop to use)
- **Customer, Sales Order, Quotation** — the order pipeline
- **Sales Taxes and Charges Template** — tax calculation

**What was extracted to `frappe/webshop` in v15 (no longer in ERPNext core):**
- Website Item (DocType + controller)
- Shopping Cart logic
- Product filter engine
- Variant selector
- All-products page
- Shop-by-category page
- Webshop Settings

Per the official ERPNext v15 setup documentation: "If you are on version 15 or are migrating to version 15, you need to install the Frappe's Webshop app first in order to use the e-commerce features."

## 9. Variant Selector — Documented UX Behavior

From `variant_selector/utils.py` (whitelisted API):

- `get_attributes_and_values(item_code)` — returns valid attribute options for a template item
- `get_next_attribute_and_values(item_code, selected_attributes)` — returns matching variants, pricing info, inventory quantity (not images)

The variant selector modal shows all attributes simultaneously. As the user selects each attribute value, the remaining options are narrowed (set intersection). When all required attributes are selected, the variant item code is resolved. The user then confirms and is redirected to `?variant=ITEM_CODE` (full page reload).

**There is no documented attribute conditional display** — i.e., no mechanism to show Attribute B only after Attribute A is selected, or to hide Attribute B when Attribute A = "Balloons" vs "Garlands."

The translation of the variant selector modal is not supported per community discussion (issue #265): "Explore button, variants item card on webshop is not translatable" (open).

## 10. Frappe Framework Primitives — Whitelist Security and File Handling

**`@frappe.whitelist(allow_guest=True)`** — Documented. Makes a Python function callable via AJAX from the browser without authentication. The webshop's cart module uses this for `create_lead_for_item_inquiry`, `apply_coupon_code`, `remove_coupon_code`. The maintainer's issue #272 flags that many endpoints use `allow_guest=True` with `flags.ignore_permissions = True`, which is a security concern.

**File DocType (Frappe):** Frappe supports attaching multiple files to a single record via the File DocType (`is_private`, `file_url`, `attached_to_doctype`, `attached_to_name`). There is no documented limit on files per record. However, Website Item has only one `website_image` field + one `slideshow` (link to Website Slideshow) in its schema. The Website Slideshow DocType is separate and supports multiple images in a child table — this is the documented mechanism for product gallery images. A Website Item can have one slideshow with N images.

**Frappe i18n:** Standard Frappe translation system. The webshop Variant Selector modal is pure JavaScript and lacks translation support (open issue #265 + #150).

## Gaps and Unknowns

1. **Official docs are nearly silent on variant image handling.** The docs.frappe.io/erpnext/user/manual/en/website_item page describes slideshow behavior but does not address per-variant image management or attribute-based image swap. This gap is confirmed both by docs and by source code inspection.

2. **No documented JS hook system for product pages.** The only extension points are CSS/JS injection via `web_include_css`/`web_include_js` and template file overrides. There is no published event bus or documented JS callback system for product page interactions.

3. **Webshop Settings has no variant-image configuration options.** None of the 20+ configurable settings relate to image display per variant.

4. **Official docs do not cover the `variant_selector` modal in any end-user documentation.** The only mention is in the E-Commerce Settings page: "Enable Variant Selection: Show a configure button if the Item has variants."

5. **No documentation on scaling limits.** There is no official guidance on what happens with 10,000+ variants in the product data engine. The query engine filters by `variant_of is not set` (hiding variants from listings when `hide_variants` is enabled) but the performance characteristics are undocumented.

6. **Frappe docs page 404:** `docs.frappe.io/framework/v15/user/en/api/override-standard-doctypes` returned 404. This documentation page is missing.

7. **No official documentation on overriding product detail page.** Website Item pages are generated by the Website Generator (WebsiteGenerator subclass). Template overrides follow the standard portal page precedence rule (custom app `www/` folder wins), but this is not documented in webshop-specific docs.

**Found — Official maintainer:**

**Found — Open GitHub issues documenting UX failures:**

**Not found:**
- Any official "limitations" section in webshop documentation
- Any official migration guide suggesting moving away from webshop

### The Canonical Answer on Variant Images

The official documentation is silent on "per-variant image swap" as a feature. The source code confirms this is not implemented. The closest available mechanism is:
1. Create a Website Item for each variant (not just the template)
2. Upload a distinct `website_image` to each variant's Website Item
3. Accept that variant image changes require a full page reload (via configure modal → confirm → URL redirect)

For LT's 10,227 active variants, mechanism (1) + (2) is operationally implausible without automation. And even with automation, the UX is a full page reload — not the color-pick → live hero swap that modern ecommerce customers expect.

### The Canonical Answer on Color Combinations

ERPNext's Item Attribute + Item Variant model natively handles multi-attribute combinations as distinct SKUs. "Pearl White 11-inch" and "Mocha 11-inch" are two different variant records with two different item codes and two different Item Price records. The data model is sound. The display UX (swatch → live image + price update without reload) is not natively supported.

### Architecture Assessment

Frappe Webshop is a server-rendered Jinja application with:
- No documented frontend event bus
- No live variant swap (redirect-based)
- No color swatch UI
- Multiple open UX bugs in cart
- The official maintainer recommending a headless rewrite

The extensibility surface (override_whitelisted_methods, override_doctype_class, template file overrides, web_include_js) is real and documented — custom JS can be injected to add swatch-style UI and AJAX variant switching on top of the existing Webshop infrastructure. But this is custom development against an undocumented frontend, not extension of a documented API.

The alternative ecommerce apps in the Frappe ecosystem are either sync connectors (Shopify/WooCommerce integrations) or unofficial third-party themes (Ecommerce Theme). There is no official Frappe-org alternative to Webshop for building a native Frappe storefront with richer variant UX.
